# WorkProof（开源证人）阶段开发说明

> 更新日期：2026 年 11 月 7 日。本文依据当前工作区、GitHub Actions 结果和本机交付记录整理。已实现、已测试和已安装是三个不同状态，下文分别说明。

## 一、项目定位与当前进展

WorkProof 面向课程作业、论文与内容写作、设计交付等场景，记录作品形成过程中的编辑事件，将过程记录与最终文件绑定，并提供可独立复核的证据文件。

项目的价值在于：让接收者除了看到最终成品，还能了解创作过程的连续性、修改轨迹、集中写入等情况，获得可核对、可解释的过程材料。

当前适合将其介绍为**创作过程记录与证据核验工具**。它尚不能独立认证作者身份、证明所有操作由人完成，或保证作品没有使用 AI。“100% 人类创作证明”“官方认证原创”均不属于现阶段已经建立的能力。

目前已经形成桌面工作台、内置编辑器、多宿主采集适配、独立核验网页与机构后台的整体结构。Windows 桌面版已在本机实际启动并交付使用；部分新功能已在源码中完成并通过远程检查，但尚未更新到这份本机安装。

## 二、现阶段已经开发的内容

### 1. Windows 桌面工作台

桌面端采用 Tauri 与 Rust，界面使用 WebView 和 Fluent 组件体系，保留现代 PC 软件的导航、窗口按钮、设置页及托盘交互。

已经实现的主要功能包括：

- 深色、浅色主题切换，统一的窗口操作按钮和直立图标。
- 可折叠的导航、工具栏、大纲和操作侧栏，以及减少动态效果设置。
- 托盘入口、连接审批、授权撤销、记录服务状态和保存后退出流程。
- 在应用内打开核验页，减少桌面与浏览器之间的切换。
- 内置文档与外部应用记录的统一列表、搜索、来源筛选和记录批次查看。
- Word、PowerPoint 原生加载项的用户级注册与桌面配置入口。

品牌图标已经通过 ImageGen 生成并接入相关界面与交付资源。Fluent 适配限定在桌面及桌面内嵌核验页，独立网页保留与管理端统一的视觉风格。

当前本机运行版本为 `d636014`，安装目录为 `E:/work/WorkProof-Delivery/WorkProof-PC-d636014`。该版本已包含过程检验单、多边形概览和参考范围横条。此后的时间凭据直接申请、信任状态细分与回执工具，不应视为已经安装到本机。

### 2. 内置编辑器与编辑过程记录

编辑器接入 Tiptap、StarterKit 及现成扩展，提供 Word 风格的富文本编辑与 Markdown 工作区，也支持接近 Typora 的精简编辑模式。

现有功能覆盖常用字体和段落格式、标题、列表、任务项、表格、链接、代码高亮、分页和分页符；可以导入 DOCX，并导出 HTML、Markdown、DOCX 及对应的 `.wproof` 证据文件。DOCX 转换复用开源插件，在独立 Worker 中执行，不依赖云端转换。

记录范围包括文字增删、格式与结构调整、撤销和重做、退格、空格、回车、复制粘贴命令、选区、焦点、拖放、输入法事件，以及编辑器分发的事务。这里的“命令被触发”不等于系统动作一定执行成功。

正文、原始动作和版本检查点保存在本机。界面会把连续或重复动作合并为可读流程，减少刷屏；合并只影响展示，不代替原始记录。历史版本与过程预览也已接入。

### 3. 宿主软件适配

不同软件的开发和验收程度并不相同，不能统称为“所有版本全部支持”。

| 宿主 | 当前实现 | 仍需补齐的部分 |
| --- | --- | --- |
| Word | 已有 Windows 原生加载项、功能区和记录面板，能够与桌面端连接；本机已更新注册 | 更多版本、DPI、长文档、休眠恢复和实际使用流程验收 |
| PowerPoint | 已有原生加载项、结构变化采集及桌面入口；本机已更新注册 | 不同 Office 版本与真实演示文稿操作覆盖 |
| WPS | 已有共享采集页面、功能区入口和发布资源；已修复功能区响应开头的兼容问题 | 首次安装入口、SDK 分发许可材料和真实宿主验收 |
| VS Code | 已有文档变更采集、连接与证据导出，具备集成测试记录 | 更复杂工作区、异常恢复和长期使用体验 |
| Photoshop | 已有 UXP 开发适配、部分图层统计和交付绑定能力 | 真实宿主全面验收、正式插件分发与更多操作覆盖 |
| Blender | 已有 Python 适配、结构统计和部分视口变化记录，具有真实 Blender CI 验证 | 更完整的演进表达、跨版本覆盖和复杂项目验收 |

宿主 API 无法提供的信息会形成采集边界。Word/WPS 的轮询采样不能被解释为逐键生物特征，更不能与内置编辑器的事件精度等同。

### 4. 证据生成、核验与可视化

本地核心已经实现文件指纹、记录哈希链、Ed25519 签名及 Merkle 选择性披露。接收者可以在浏览器内通过 Rust/Wasm 核对作品与证据，核心核验流程无需上传作品。

已经实现的展示包括：

- 文件选择、证书选择、结果与分享的步骤引导。
- 大字号证书、证书指纹、原始签名文件与部分证据分享。
- 编辑过程提醒，以及新增量、删除量、内容规模和写入速率的时间轨迹。
- 位于轨迹图上方的完整检验单：测量值、单位、参考条件、异常箭头及红色提醒。
- 五项过程特征的多边形概览，以及带参考阈值的横条。

多边形与横条表示相对规则阈值的位置，不是原创分数、能力评分或 AI 百分比。样本不足的项目不绘制伪造数值；部分披露不冒充完整创作过程。

最新网页源码还把“文件与签名一致”“官方来源”“采集真实性”“规则有效性”分别展示，避免一个绿色通过状态包办所有结论。此项网页更新已通过测试，尚未切换本机桌面安装。

### 5. 时间凭据、C2PA 与服务器回执

时间凭据已经具备请求生成、手工提交和本地独立核验。新增的直接申请入口允许用户填写 HTTPS 时间服务地址并主动发送，仅提交签名摘要与随机编号；具有取消、超时、响应类型和大小限制。接收响应后仍需选择独立取得的 CA 并确认信任，不会自动认定服务可信。最新实现已通过 114 项浏览器检查。

C2PA 方面，已有独立 Rust 工具，PNG、JPEG 和受限 PDF 的签署与核验具有 Linux、Windows、macOS Intel/ARM 的验证记录；浏览器也已接入三种格式的 Worker/Wasm 核验入口，检查完整与部分证据、错误 CA 和篡改拒绝。PDF 使用严格增量封装，保留原件字节，但明确拒绝加密、已有数字签名等不支持的输入，不能概括成所有文件格式均支持。真实系统文件选择器的完整人工流程仍需验收；正式签署依赖合法的签名证书、私钥及接收方独立信任策略，不代表已取得公共权威认证。

服务器回执的底层协议已经实现并通过测试。回执绑定接收到的证据原始字节、原签名、作品声明指纹、会话、披露范围和有效期，核验者必须独立提供可信公钥。

一次性回执命令行工具也已写入源码，但**尚未完成集成验收**：最新检查中编译和协议测试通过，命令行集成步骤因 CI 缺少示例证书文件而失败，需要修复后复验。机构签发接口、可信根发布、密钥轮换、吊销与设备远程证明尚未接入。

服务器签过回执，只能说明该签发者接收并签署了所绑定的数据，不能直接证明数据来自官方客户端或每项操作真实发生。

### 6. 机构后台

机构服务基于 `wbr664393425-lgtm/scaffold-master` 底座进行整合，采用 Spring Boot 与 Vue，并与 Rust 本地记录引擎分离。已有登录、权限、部门数据范围、审计等基础能力，以及证书内容检查、摘要索引、查询、详情、CSV 导出和页面内批量处理。

证书检查复用 Rust 核验工具，避免在 Java 中重新实现密码学算法。证书摘要业务按账号及部门范围隔离；数据库迁移需要显式准备，不自动改写既有生产数据。

机构端也有可选 AI 辅助分析入口和独立进程调用链。它与作品签名核验分别展示，用户需明确同意发送分析材料。

部分机构功能具有真实数据库、JAR、权限和网页链路的 CI 验证记录，但正式服务器部署、运行凭据、HTTPS、模型启用和本机版本更新，仍需逐项核对。页面内批量处理不等同于关闭浏览器后仍可持续运行的服务端任务。

### 7. AI 辅助判断与文件线索

现有可选模型流程包括 MPU 中文、MPU 英文和 Desklib 英文。这些适配具有真实模型调用及机构流程验收记录，但均属于监督分类，不能把三个模型称为三种独立检测方法，更不能宣传为已经覆盖大多数开源检测引擎。

项目也开展了基于 Qwen3-0.6B-Base 的 LRR 统计方法实验。独立留出评估中，中文漏报约 79.17%，英文漏报约 90.63%，当前配置效果不足，因此没有作为正式检测功能启用。这项结果说明：模型能运行、能输出数值，不等于能可靠识别 AI 内容。

本机文件线索检查已经覆盖 PNG 文字字段、JPEG 部分 EXIF/注释/XMP，以及 DOCX/PPTX 的指定文档属性。提示词、工作流或生成器相关字段只能作为可修改的来源线索；普通办公软件名称不直接标为 AI 证据。当前没有通用的未知厂商水印识别能力，也没有完成全模态可靠检测。

## 三、现阶段的功能特色

**过程证据与检测分数分开。** 文件匹配、签名、行为提醒、元数据和模型结果各自说明依据，避免用一个分数替代全部判断。

**本机记录与离线核验优先。** 内置编辑内容和原始动作留在本机，核心核验可在浏览器本地完成；需要联系时间服务或机构分析时，由用户明确触发。

**跨应用记录统一查看。** 内置编辑器和外部宿主的记录进入同一文档列表，同时保留各自的采集精度与能力边界。

**可携带、可复核、可选择披露。** 接收方可以核对签名和文件，不依赖一张证书截图；分享者可以减少披露事件，但不能因此声称未公开部分也经过完整检查。

**重视普通用户的阅读体验。** 通过步骤引导、较大文字、动作合并、检验单、轨迹和参考横条，帮助接收者找到需要解释的片段，而不是要求其自行理解哈希或统计公式。

## 五、必须明确的局限

### 1. 自签名不能证明官方来源

当前本机密钥能够保证签名数据的一致性，却不能阻止另一个程序自行生成密钥、构造记录并签名。密钥文件的本机访问保护也不能代替运行环境证明。记录未被篡改，与记录是否真实，是不同问题。

### 2. 行为异常不能直接认定 AI 创作

当前过程提醒使用启发式阈值，尚未在真实中英文课程作业中完成校准。正常粘贴、资料导入、语音输入、辅助工具、代码补全和宿主采样都可能产生类似曲线。当前不能给出可靠的“人类创作比例”或“AI 使用比例”。

### 3. 记录覆盖和耐久性存在边界

不同宿主不能观测同样精度的事件；启动记录之前的历史无法补造。内置编辑器采用批量自动保存，断电或强制终止仍可能损失最后一小段尚未提交的操作。部分网页加载项的未提交队列仍依赖面板内存，持久恢复尚需完善。

### 4. 格式转换与宿主兼容不是完全无损

DOCX 常用正文和格式已具备转换能力，但复杂页眉页脚、图片定位、批注、修订和分节版式不能承诺与 Word 完全一致。各宿主不同版本、系统权限及首次安装路径仍需实机验证。Windows 外观使用 Fluent Web 组件，不是原生 XAML 实现。

### 5. “超轻量”必须按运行状态衡量

Rust 主进程、托盘空闲状态、打开 WebView、运行编辑器和加载 AI 模型具有不同资源开销。不能把某次托盘工作集结果用来代表完整桌面编辑状态，更不能把模型分析的资源占用算作始终轻量。设计目标尚需靠持续测量和优化达成。

### 6. 商用与部署尚未整体放行

核心与多项组件已有开源许可及归档记录，但上游 WPS 工具、部分模型血缘、训练数据与实际分发依赖仍有待核对项。代码、模型权重、数据和品牌权利需要分别审查，不能以顶层 MIT 或某个依赖允许商用就推导整个产品无条件商用。

正式部署还需要合法宿主软件、机构服务器配置、域名与 HTTPS、独立签发密钥及相应服务凭据。测试密钥、合成 CA 和测试服务器都不能冒充生产权威。

## 六、下一步开发方向

### 优先级一：把已有功能完成交付闭环

修复回执命令行集成测试缺失示例证书的问题，完成真实工具往返复验；整理版本、安装包与验收范围，交付包含最新信任说明和时间凭据入口的桌面版。继续进行 Windows 真实编辑、文件拖入、关闭保存、断网恢复与宿主侧栏验收，优先处理普通用户无法开始或无法理解的流程。

### 优先级二：建立可信签发与来源体系

将回执接入机构受控接口，补齐权限、审计、签发记录、独立可信公钥发布、轮换和吊销。生产签发私钥留在服务器或受控密钥设施中，客户端不内置通用官方私钥。

随后加入会话随机挑战、分批摘要提交、序号与防重放、分叉检查。硬件密钥与远程证明应作为进一步提升保证的能力，按平台实际支持范围实施。即使完成这些工作，也要继续区分“服务接收过”“客户端运行环境通过策略检查”和“人类亲手创作”。

### 优先级三：验证规则是否真的有效

组织经授权的真实中英文创作过程，覆盖办公软件、内置编辑器、正常导入、输入法、辅助输入、AI 辅助与脚本模拟。按作者、文档和任务划分独立测试集，冻结阈值后再评估。

报告应分组公开样本量、误报率、漏报率和置信区间，明确不适用场景。AI 引擎接入优先考虑具有近期评估依据、许可可核验和资源预算可接受的方法；效果不足的实验继续保持不启用，不为追求引擎数量强行上线。

### 优先级四：完成宿主和格式能力

按 Word、WPS 优先的顺序完善首次安装、直接打开文档并开始记录、长期运行和异常恢复。继续补充 PowerPoint、VS Code、Photoshop、Blender 的真实宿主覆盖；完善 DOCX 兼容、结构演进和可视化，但不自行重写已有成熟格式转换组件。

### 优先级五：形成机构试点与可持续部署

完善服务器批量任务、队列持久化、备份恢复、私钥管理、部署包与跨平台说明。完成第三方许可清单和未决项处理，在小范围真实课程或交付场景中试点，记录使用成本、教师理解程度、争议处理和误报反馈。

项目下一阶段的重点，是把已有能力逐步转化为**能稳定使用、结论可解释、边界可核对的可信工具**。功能数量和视觉展示需要继续服务于这件事。
